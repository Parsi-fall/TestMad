## [2026-10-11 21:31:00 +06:00] Этап 0: Инициализация проекта и инфраструктура окружения

### Что сделано:
1. Создана структура монорепозитория:
   - `backend/` — каркас микросервиса на FastAPI с Pydantic Settings и Healthcheck-эндпоинтом.
   - `frontend/` — каркас SPA на React 18, Vite и TypeScript.
   - Корневой `docker-compose.yml` и конфигурация `.env.example`.
2. Настроены контейнеры:
   - `db` (PostgreSQL 16 Alpine) с healthcheck (`pg_isready`).
   - `mailhog` (MailHog) для перехвата SMTP-сообщений (`:1025`) и чтения через REST API / Web UI (`:8025`).
   - `backend` (FastAPI/Uvicorn) с монтированием тома для мгновенной горячей перезагрузки (`reload`).
   - `frontend` (Node 20 / Vite dev-сервер) с поддержкой polling для файловых систем Docker.
3. Оформлена базовая документация: честный чеклист статуса в `README.md` и данный журнал решений `DECISIONS.md`.

### Почему выбраны такие решения:
1. **Docker Compose как единая точка запуска:**
   - *Причина:* Полная изоляция зависимостей. Проверяющему не нужно устанавливать локально PostgreSQL или MailHog — всё поднимается командой `docker compose up --build`.
2. **MailHog вместо реального почтового сервера:**
   - *Причина:* Исключает необходимость в реальных SMTP-креденшелах, внешних сервисах (SendGrid, Mailgun) и исключает риск попадания в спам. Предоставляет JSON API, благодаря которому демо-скрипты и автотесты могут проверить доставку писем программно.
3. **FastAPI (асинхронный) + React Vite:**
   - *Причина:* FastAPI нативно поддерживает WebSockets и асинхронную работу с базой через `asyncpg`, что критично для поддержания live-счетчиков и тестирования параллельной конкурентности. Vite обеспечивает быструю сборку и HMR.

## [2026-10-11 21:34:00 +06:00] Этап 1: База данных, ORM модели и миграции Alembic

### Что сделано:
1. Настроена асинхронная сессия SQLAlchemy 2.0 (`app.core.database`) с поддержкой пулов и `AsyncSessionLocal`.
2. Созданы декларативные модели сущностей:
   - `Event` (`app.models.event`): поля `id` (UUID), `title`, `description`, `event_date`, `capacity` (с ограничением `CHECK (capacity > 0)`).
   - `Registration` (`app.models.registration`): поля `id`, `event_id`, `email`, `status` (`confirmed`, `waitlist`, `cancelled`), `cancel_token` (уникальный 64-значный токен для безопасной отмены в 1 клик), `reminder_sent_at` (флаг однократного напоминания).
   - `Ticket` (`app.models.ticket`): поля `id`, `registration_id` (1:1 связь), `ticket_code` (короткий уникальный код прохода), `is_checked_in`, `checked_in_at`.
3. Заданы критические ограничения и составные индексы:
   - `UniqueConstraint("event_id", "email")`: исключает двойную регистрацию на уровне СУБД.
   - `Index("ix_registrations_event_status_created", "event_id", "status", "created_at")`: обеспечивает мгновенную выборку первого кандидата из очереди FIFO при освобождении места.
   - `UniqueConstraint("ticket_code")`: мгновенный поиск билета на чекине.
4. Настроен Alembic с асинхронным `env.py` и подготовлена первая миграция `0001_initial_schema`.
5. Реализован модуль автоматической инициализации и сидинга `init_db.py`, создающий при старте тестовое мероприятие с лимитом 5 мест.

### Почему выбраны такие решения:
1. **Вынос билета (`Ticket`) в отдельную сущность от регистрации (`Registration`):**
   - *Причина:* Участник в статусе `waitlist` зарегистрирован, но у него нет права на проход и нет кода билета. Разделение сущностей исключает хранение `NULL`-кодов, случайное использование кода из очереди и чётко разделяет жизненные циклы заявки и билета.
2. **Токен отмены (`cancel_token`) вместо авторизации:**
   - *Причина:* Для сервиса регистрации без постоянных аккаунтов ввод паролей пользователем — избыточный барьер. Криптографически стойкий `token_urlsafe` в ссылке из письма решает задачу авторизации безопасным и удобным для посетителя способом.
3. **Индекс `(event_id, status, created_at)`:**
   - *Причина:* Позволяет СУБД без полного сканирования таблицы находить самого первого ожидающего участника для перевода из waitlist в confirmed (`ORDER BY created_at ASC LIMIT 1`).
