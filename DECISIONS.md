## [2026-10-11 21:31:00 +06:00] Этап 0: Инициализация проекта и инфраструктура окружения

### Что сделано:
1. Создана структура монорепозитория:
   - `backend/` — каркас микросервиса на FastAPI с Pydantic Settings и Healthcheck-эндпоинтом.
   - `frontend/` — каркас SPA на React 18, Vite и TypeScript.
   - Корневой `docker-compose.yml` и конфигурация `.env.example`.
2. Настроены контейнеры:
   - `db` (PostgreSQL 16 Alpine) с healthcheck (`pg_isready`).
   - `mailhog` (MailHog) для перехвата SMTP-сообщений (`:1025`) и чтения через REST API / Web UI (`:8025`).
   - `backend` (FastAPI/Uvicorn) с монтированием тома для мгновенной горячей перезагрузки (`reload`).
   - `frontend` (Node 20 / Vite dev-сервер) с поддержкой polling для файловых систем Docker.
3. Оформлена базовая документация: честный чеклист статуса в `README.md` и данный журнал решений `DECISIONS.md`.

### Почему выбраны такие решения:
1. **Docker Compose как единая точка запуска:**
   - *Причина:* Полная изоляция зависимостей. Проверяющему не нужно устанавливать локально PostgreSQL или MailHog — всё поднимается командой `docker compose up --build`.
2. **MailHog вместо реального почтового сервера:**
   - *Причина:* Исключает необходимость в реальных SMTP-креденшелах, внешних сервисах (SendGrid, Mailgun) и исключает риск попадания в спам. Предоставляет JSON API, благодаря которому демо-скрипты и автотесты могут проверить доставку писем программно.
3. **FastAPI (асинхронный) + React Vite:**
   - *Причина:* FastAPI нативно поддерживает WebSockets и асинхронную работу с базой через `asyncpg`, что критично для поддержания live-счетчиков и тестирования параллельной конкурентности. Vite обеспечивает быструю сборку и HMR.

## [2026-10-11 21:34:00 +06:00] Этап 1: База данных, ORM модели и миграции Alembic

### Что сделано:
1. Настроена асинхронная сессия SQLAlchemy 2.0 (`app.core.database`) с поддержкой пулов и `AsyncSessionLocal`.
2. Созданы декларативные модели сущностей:
   - `Event` (`app.models.event`): поля `id` (UUID), `title`, `description`, `event_date`, `capacity` (с ограничением `CHECK (capacity > 0)`).
   - `Registration` (`app.models.registration`): поля `id`, `event_id`, `email`, `status` (`confirmed`, `waitlist`, `cancelled`), `cancel_token` (уникальный 64-значный токен для безопасной отмены в 1 клик), `reminder_sent_at` (флаг однократного напоминания).
   - `Ticket` (`app.models.ticket`): поля `id`, `registration_id` (1:1 связь), `ticket_code` (короткий уникальный код прохода), `is_checked_in`, `checked_in_at`.
3. Заданы критические ограничения и составные индексы:
   - `UniqueConstraint("event_id", "email")`: исключает двойную регистрацию на уровне СУБД.
   - `Index("ix_registrations_event_status_created", "event_id", "status", "created_at")`: обеспечивает мгновенную выборку первого кандидата из очереди FIFO при освобождении места.
   - `UniqueConstraint("ticket_code")`: мгновенный поиск билета на чекине.
4. Настроен Alembic с асинхронным `env.py` и подготовлена первая миграция `0001_initial_schema`.
5. Реализован модуль автоматической инициализации и сидинга `init_db.py`, создающий при старте тестовое мероприятие с лимитом 5 мест.

### Почему выбраны такие решения:
1. **Вынос билета (`Ticket`) в отдельную сущность от регистрации (`Registration`):**
   - *Причина:* Участник в статусе `waitlist` зарегистрирован, но у него нет права на проход и нет кода билета. Разделение сущностей исключает хранение `NULL`-кодов, случайное использование кода из очереди и чётко разделяет жизненные циклы заявки и билета.
2. **Токен отмены (`cancel_token`) вместо авторизации:**
   - *Причина:* Для сервиса регистрации без постоянных аккаунтов ввод паролей пользователем — избыточный барьер. Криптографически стойкий `token_urlsafe` в ссылке из письма решает задачу авторизации безопасным и удобным для посетителя способом.
3. **Индекс `(event_id, status, created_at)`:**
   - *Причина:* Позволяет СУБД без полного сканирования таблицы находить самого первого ожидающего участника для перевода из waitlist в confirmed (`ORDER BY created_at ASC LIMIT 1`).

## [2026-10-11 21:38:00 +06:00] Этап 2: Регистрация, идемпотентность, конкурентность и отправка почты

### Что сделано:
1. Реализован сервис отправки почты (`app.services.mailer`) через `aiosmtplib` с отправкой multipart (HTML + Plain text) писем с уникальным кодом билета и ссылкой для отказа от участия (`cancel_token`).
2. Разработан генератор читаемых кодов билетов (`app.utils.code_generator`): формат `TKT-XXXXXX` с алфавитом без визуально неразличимых символов (`0`, `O`, `1`, `I`, `L`) для удобного ручного ввода.
3. Реализована транзакционная логика регистрации (`app.services.registration`):
   - Использование `SELECT FOR UPDATE` для блокировки строки мероприятия в PostgreSQL на время транзакции (с graceful fallback для SQLite в тестах).
   - Проверка лимита `confirmed_count < capacity`.
   - Идемпотентность по email: повторный запрос с тем же email не создает дублирующее место, а возвращает существующий билет и повторно отправляет письмо.
   - Автоматический перевод в `waitlist` при превышении лимита с расчётом номера в очереди FIFO.
4. Настроены REST API эндпоинты (`/api/v1/events`, `/api/v1/events/{id}/register`, `/api/v1/registrations/by-token/{token}`).
5. Добавлены и успешно пройдены модульные тесты:
   - `test_registration_and_idempotency` — проверка создания билета, неизменности при повторной регистрации, подсчета мест.
   - `test_concurrent_registration_for_last_spot` — параллельный запуск конкурентных запросов через `asyncio.gather` на единственное оставшееся место: ровно 1 получил подтверждение, остальные 4 гарантированно ушли в `waitlist` без овербукинга.

### Почему выбраны такие решения:
1. **Пессимистическая блокировка `FOR UPDATE` вместо оптимистической (`version` column):**
   - *Причина:* При оптимистической блокировке второй клиент получил бы ошибку конфликта (409) и должен был бы делать retry. В нашем случае второй клиент не должен получать ошибку: он должен бесшовно встать в очередь ожидания (`waitlist`). Пессимистическая блокировка сериализует запросы на уровне Postgres за миллисекунды и обеспечивает идеальный пользовательский опыт.
2. **Алфавит кода билета без путающихся символов:**
   - *Причина:* По условиям ТЗ на чекине используется ручной ввод кода контролёром. Исключение похожих символов (ноль и 'O', единица и 'I') предотвращает человеческие ошибки при вводе.
3. **Идемпотентная повторная отправка письма:**
   - *Причина:* Если участник случайно потерял письмо или нажал кнопку регистрации второй раз, система не выдаёт ошибку и не отнимает место у других, а просто пересылает ему ранее выданный билет.

## [2026-10-11 21:39:00 +06:00] Этап 3: Отмена участия и автоматическое продвижение из листа ожидания (FIFO)

### Что сделано:
1. Создан сервис управления очередью ожидания (`app.services.waitlist`):
   - Поиск регистрации по секретному токену (`cancel_token`).
   - Идемпотентность отмены: если заявка уже отменена, возвращается понятный статус без ошибок.
   - Транзакционная защита: событие блокируется на время отмены для предотвращения гонки с новыми внешними регистрациями.
   - Освобождение места: статус текущего участника меняется на `cancelled`, его билет аннулируется.
   - Выборка первого в очереди кандидата в строгом хронологическом порядке (`ORDER BY created_at ASC LIMIT 1`).
   - Автоматический промоут: статус кандидата переводится в `confirmed`, генерируется новый читаемый билет (`TKT-XXXXXX`), формируется и отправляется поздравительное письмо с билетом.
   - Мгновенное обновление счетчиков организатора через WebSocket.
2. Реализован API эндпоинт `POST /api/v1/registrations/cancel/{cancel_token}`.
3. Написан тест `tests/test_cancellation.py`:
   - Заполнение события до лимита (1 место).
   - Постановка двух пользователей в `waitlist` (очередь 1 и 2).
   - Отмена регистрации основного участника: проверка, что первый кандидат автоматически стал `confirmed` и получил билет, а второй остался в `waitlist`.
   - Проверка повторной отмены (идемпотентность).

### Почему выбраны такие решения:
1. **Транзакционное объединение отмены и промоута:**
   - *Причина:* Если бы отмена и назначение нового участника происходили в двух раздельных операциях, между ними образовалось бы «окно уязвимости», когда случайный сторонний посетитель мог бы перехватить освободившееся место в обход накопившейся очереди ожидания. Единая транзакция с блокировкой события гарантирует строгое соблюдение прав людей из листа ожидания.
2. **Строгий FIFO по `created_at ASC`:**
   - *Причина:* Честный принцип очерёдности «первым пришёл — первым обслужен». Составной индекс `(event_id, status, created_at)` обеспечивает моментальную выборку даже при тысячах заявок в очереди.

## [2026-10-11 21:40:20 +06:00] Этап 4: Чекин билетов и Live-обновления для организатора (WebSockets)

### Что сделано:
1. Создан сервис чекина билетов (`app.services.checkin`):
   - Санитизация кода: обрезка пробелов и приведение к верхнему регистру (`upper()`).
   - Проверка существования билета (404) и валидности статуса регистрации (400 при `cancelled` или `waitlist`).
   - Защита от повторного входа: если билет уже использован, возвращается ошибка `409 Conflict` с указанием точного времени первого прохода.
   - Атомарная фиксация факта чекина (`is_checked_in = True`, `checked_in_at = NOW()`).
2. Разработан WebSocket-роутер (`app.api.v1.ws`) и менеджер трансляций:
   - Эндпоинт `/api/v1/ws/events/{event_id}` для live-дашборда организатора.
   - При подключении клиент мгновенно получает текущее состояние метрик (`confirmed`, `waitlist`, `checked_in`).
   - При любых изменениях (регистрация, отмена, чекин) бэкенд мгновенно отправляет обновлённый снапшот всем подключённым вкладкам организатора.
3. Добавлен REST API эндпоинт `POST /api/v1/checkin` для ручного ввода кода.
4. Написан тест `tests/test_checkin.py`:
   - Успешный первый чекин с ростом счетчика `checked_in_count`.
   - Отклонение повторного ввода того же билета с кодом 409.
   - Обработка невалидных кодов и проверка нечувствительности к регистру и пробелам.

### Почему выбраны такие решения:
1. **WebSockets вместо Polling:**
   - *Причина:* Polling с фронтенда каждые N секунд нагружает сервер пустыми GET-запросами и дает видимую задержку для организатора. WebSocket обеспечивает мгновенное появление отчекиненного человека на экране организатора (< 10 мс) и нулевой трафик в покое.
2. **Возврат времени первого чекина в сообщении об ошибке (409 Conflict):**
   - *Причина:* Для работы контролёра на входе критически важно видеть: «Билет уже был использован в 18:42:15», чтобы пресекать попытки пройти по скриншоту чужого билета.
